## 一次資料とローカル仕様

メーカー資料：
- https://www.feetechrc.com/20210430-56680.html （STS3215のフィードバック、保護動作）
- https://www.feetechrc.com/Data/feetechrc/upload/file/20220618/先看这里-入手教程2-1.pdf
  （メーカー導入資料のSTSメモリ説明。検索抽出で温度・Status等を確認、全文取得はタイムアウト）

| 項目 | ローカルアドレス/長さ | 解釈 |
|---|---|---|
| Present_Current | 69 / 2 bytes | メーカーSTS3215説明ではraw×6.5mA |
| Present_Load | 60 / 2 bytes | 駆動出力デューティ指標。絶対値1000が100%。実トルク・指先力の測定値ではない |
| Present_Temperature | 63 / 1 byte | 内部温度、1℃単位。指先温度ではない |
| Present_Voltage | 62 / 1 byte | raw×0.1V |
| Status | 65 / 1 byte | bit0電圧、1センサ、2温度、3電流、4角度、5過負荷。1が該当異常 |

実機の型番・ファームウェアとの一致確認は未実施。生値と換算値、資料版を併記するのがよい。
ローカルLeRobotはPresent_Loadのbit10を符号として復号する。負値を二の補数と解釈し直さない。
Current/Voltageを自動的にmA/Vへ変換する実装はないため、表示側で換算する必要がある。
Status=0は接触なし・安全な力を証明しない。電流は摩擦・機構・速度等にも依存する。
メーカー説明の電流保護では力を解放し、次の指令で保護解除される場合があるため、保護を当てにして
Goal_Positionを送り続ける方針は採用しない。個体での保護動作は未確認。

既存configureはMax_Torque_Limit=500、Protection_Current=250、Overload_Torque=25を書いている。
電流についてメーカー換算なら250は1.625Aに相当するが、これを安全な把持電流と認定しない。
今回は書込み・読取りとも実機では実行していない。

## グリッパだけの診断と通信量

ローカルAPIの `bus.read('Present_Current', 'gripper', normalize=False, num_retry=0)` のように、
ID6だけの読取りが可能。他の4レジスタも同様。実行例ではなくAPI確認であり、実機には呼んでいない。
保護ラッパーは現在6軸固定の診断メタデータなので、採用時にはID6の対象表示と追加レジスタを正しく扱う必要がある。
失敗時は既存の送信禁止ラッチに統合し、別スレッドからバスへ並行アクセスしない。

5項目を20Hzで読むと追加100取引/秒。Followerの位置/トルク40取引/秒に対し合計140取引/秒となる。
1Mbps・8N1で5項目の要求/応答合計77byteは線上で約0.77msだが、返答待ち・USB・OS処理を含まない下限。
正常時の実測は実機承認後に行う。既存muhi-session-002では6軸位置の平均約1.23ms、
トルク約1.00msだったが、これをID6の5項目読取り時間と同一視しない。
1読取りタイムアウトは概ね50ms台、診断再試行を加えると100ms台以上になり得る。

最初は5項目を各2Hz程度の観測用途として、順番に1項目ずつ取得する案なら追加10取引/秒。
ただし更新間隔500msは過負荷保護の根拠にできず、初回から閉ループ制御へ使わない。
実測位置・Torque_Enableの20Hz監視は維持する。失敗したら制御停止、診断再読取り成功でも再開しない。
60〜70の11byteをまとめる案は通信量を減らせるが、LeRobotの_readは1/2/4byteのみ対応する。
新しいSDK経路・復号・異常検出の検証が必要なため、今回の最小実装には含めない。

## A：合成モデルの改善と限界

gripper_lag_model.pyは以下の仮パラメータで比較した。
- 新しい閉目標が実測から3単位より先行しないよう制限。ただし既存目標を自動的に開く方向へ戻さない。
- 実測−既存目標が3以上、閉速度が5単位/秒未満という条件が2周期続いたら接触疑いをラッチ。
- 最大目標変化30単位/秒、硬い停止上限8、接触未確認の待機上限0.5秒を維持。
- 明示的な開要求が2周期続く場合のみ制限速度で開く。自動再閉鎖なし。
- 通信異常・75ms超のサンプル間隔・値異常・上限超過でラッチ停止。回復しても自動再開しない。
- 固定した目標でも力は残る。タイムアウトは追加指令生成を止めるだけで、力を取り除く機能ではない。

これらは実機向けに検証済みのしきい値ではない。記録ランチャーへ組み込んでいない。
5軸の監視・通信停止機構も変更しない。実機採用時のactionは制限後目標、action_requestedはLeader原値とする。

合成プラント（50msごとに前目標との差の30%だけ追従、接触25、引っ掛かり40）での比較：

| 条件 | 旧モデル | 試作モデル |
|---|---|---|
| 通常追従遅れ | 0.10秒で誤検出、停止 | 接触判定なし、継続 |
| 物体接触 | 接触に達する前に誤検出 | 1.55秒で接触疑い、その後時間上限停止 |
| 引っ掛かり | 接触に達する前に誤検出 | 0.70秒で接触疑い、その後時間上限停止 |
| 極低速の自由運動＋量子化 | 誤検出 | 誤検出が残る |

極低速ケースは最大0.01単位/周期、測定を0.1単位へ丸めるもの。
通常追従で改善したのは、先行量制限で閉じ動作自体も遅くなる効果を含む。識別性能だけの改善ではない。
接触と引っ掛かりはどちらも未確認として停止する。「正常把持」と自動認定していない。
実測応答のモデル同定、電流/負荷と物体条件の実機確認なしに保持を長時間許可することはできない。
既存45件＋追加6件、計51件の非実機テスト成功。結果JSONはvalidation/options_20261018に保存。

## B：制御を変えず少数の成功デモを優先

1. 承認後、同じ物体・同じ向き・同じ挟む位置・低い持上げ高さで1エピソードずつ試す。
   落下しても危険の小さい作業面と、物体を支えられる退避手順を先に用意する。
2. 把持直前はLeaderグリッパを小刻みにゆっくり閉じ、深く握り切らない。
   最初の接触が疑われたら閉じる操作を止め、さらに締め込んで補わない。
   Leaderを止めてもFollowerは既送信目標まで動き得る。即時の力停止を意味しない。
3. 明らかな滑りがあれば成功扱いにせず、支持された状態で開放してやり直す。
   姿勢・表面摩擦を変更した場合は実験条件として記録し、学習と評価で条件を混同しない。
4. 各回直後に動画、位置・前回目標の誤差、実送信目標、Leader要求を確認する。
   最初は1本ずつ確認して成功3本を目指し、同じ傾向が再発したら量産しない。
5. 成功のPick/Place/全体ラベルを確認し、aで採用。失敗・未判定をACT学習へ混ぜない。

muhi-session-002の23前後は安全把持位置ではない。瓶の挟み方で変化するため共通の固定値にしない。
許容できる誤差・電流の安全基準は未確定。既存8の停止しきい値を緩めない。

### 表示案（まだランチャーへ未実装）

主制御で既に取得しているデータを表示用キューへ渡し、2〜5Hzで別処理から表示する。
追加シリアル読取りは不要。表示キューが詰まれば表示だけを捨て、制御はブロックしない。
`mode / measured / previous_sent / abs(measured-previous_sent) / requested / newly_sent / age_ms`を明示する。
新目標と送信前実測の差を、次周期で測定済みの追従誤差のように表示しない。
表示が古い場合はSTALEを明示。観測用であって保護・停止判定の代わりにはしない。
把持中に表示へ視線を取られすぎないよう、可能なら補助者が確認する。

### 中断方法

- `e`は記録終了のみ。TELEOP_RESETへ移り追従は続く。安全停止キーではない。
- `h`は現在位置への保持指令を伴い、把持状態を変え得る。把持力を消す方法ではない。
- Ctrl-Cは通常操作ループを終了する。通信正常時の終了処理ではグリッパ前目標を維持するため、力は残り得る。
- 通信異常時は新しい指令を送らないが、サーボは最後の目標へ動き続けたり保持したりし得る。
- 開放操作は通信・制御が正常な間に、物体を支持した状態で明示的に行う。
  異常ラッチ後に開放指令を自動送信しない。危険時は記録より支持・電源対応を優先する。
  ソフトウェアのどのキーも、物理的な即時停止・力解除を保証しない。

## 工数の比較（概算、保証ではない）

| 案 | 追加作業 | 目安 | 主な限界 |
|---|---|---|---|
| B・現行操作 | 1本ずつ確認しながら収集 | 承認後30〜90分の試験枠 | 成功本数は保証できない。握り操作依存 |
| B・表示追加 | 非ブロッキング表示＋回帰テスト | 2〜4時間 | 表示は力の安全性を保証しない |
| A・診断取得 | ID6読取り・ログ・通信ラッチ統合＋試験 | 4〜8時間＋実機観測 | 電流/負荷の安全基準は別途必要 |
| A・接触制御 | 個体評価・接触/過負荷条件・操作解除設計 | 1〜3作業日以上 | 工数不確実、持続把持の安全性未検証 |

推奨はBの表示整備と少数デモを先行。Bでも再現性のある成功が得られなければ収録を止め、
Aの読取り診断・タスク配置の見直しへ移る。Aの0.5秒停止モデルを時間制限だけ外して実機へ適用しない。
