# Codex task — SO-101 dynamic programming trajectory-level IK branch selection (offline only)

## Motivation and goal
The multistart audit at commit `b2174b32bfb9038baa7a621d38d720a60926ab93` found position residual ≤2 mm witnesses for all 186 targets per mapping under hypothetical shoulder/elbow `++` and `--`, but the **greedy per-frame** witness selector produced discontinuous joint trajectories (e.g. ++ max jump 19.601°, -- 12.039°). Test **dynamic programming (DP)** over the full 31-frame candidate sets to determine whether branch selection can improve temporal quality **without new IK optimization**. Do not claim physical mapping validity, global optimality outside the finite candidate set, or safe physical motion.

## Safety and fixed scope
- Entirely offline. No robot connection, servo registers, torques, motor commands, ACT inference/training, hardware playback, new images, or modified dataset/calibration/URDF/physical limits.
- Train-split Episode 0, frames 565–595 inclusive, 20 Hz recorded timestamps, 6 directions (URDF-world ±X/Y/Z 3 mm), four *hypothetical* shoulder/elbow sign mappings (++, -+, +-, --), offset b=0. Other joints retain identity *assumption*; all physical mappings unverified.
- The saved local candidate file `outputs/so101-ik-multistart-565-595-20261028-v2/per_seed.json` is **gitignored**; read it if available. Inspect actual schema and provenance before proceeding. Do not assume that it is present. If absent, regenerate only with existing `scripts/so101_capture/audit_mapping_ik_feasibility_offline.py` and original settings (with explicit local calibration path via `$FOLLOWER_CALIBRATION_JSON`), recording exact output path. Never commit `per_seed.json` or raw calibration values.
- **Candidate-set caveat:** previous-witness seeds in the existing multistart run depend on its greedy trajectory. DP can optimize only the recorded finite candidates, not explore all IK branches. No "globally optimal IK" language. Distinguish post-hoc candidate selection from new IK solving.
- No 648-frame expansion unless separate explicit gate passes and is reported; STOP at 31 if not.

## Implementation — candidate extraction and comparison
1. Inspect `scripts/so101_capture/audit_mapping_ik_feasibility_offline.py`, `evaluate_mapping_hypotheses_offline.py`, and the latest report/JSON. From each `per_seed.json` row collect: mapping, direction, frame, candidate motor vector (five arm joints), residual mm, feasible witness flag, orientation change degrees, active URDF bounds. Verify finite numbers, expected frames, no missing or duplicate keys that change counts. Deduplicate near-identical motor vectors *within each frame* with explicit small tolerance, keep lowest residual, deterministic tie-breaking.
2. For each mapping × direction, build a layered graph with one layer per frame and nodes = feasible witnesses (residual ≤2 mm). Transitions connect consecutive frames in timestamp order. **Do not silently substitute NOT FOUND (>2 mm) candidates as feasible.** For -+/+- identify and report infeasible layers; DP may run on maximal contiguous feasible segments but those mappings must fail the full 31-frame feasibility gate. Identify segments and coverage.
3. Implement deterministic **first-order DP** minimizing total cost:
   - data fidelity to recorded Action in **motor coordinates** (degrees);
   - inter-frame joint-angle change (ideally squared rate with actual dt);
   - optional per-candidate TCP orientation deviation as diagnostic or a declared weighted penalty, making clear tool orientation is not constrained;
   - optional bound proximity penalty (not a physical-limit certification).
   Use a documented scale normalization and predeclared weights, avoid a trivially motionless-but-far-from-recorded branch; report raw metrics alongside optimization cost. Keep the same candidate pool and feasibility definition for both greedy comparator and DP.
4. If tractable (max ~10 starts/frame × 31), implement a **second-order DP** / pair-state recurrence including discrete acceleration penalty based on actual timestamps, not only first-order velocity. Prefer compare both first-order and second-order DP against a *recomputed* greedy baseline from the exact same cached candidates, same initial conditions and deterministic tie break. No need to re-solve IK per transition.
5. **Do not falsely assume strict velocity/acceleration hard limits:** report them as diagnostics; if imposing max-jump/max-rate edges, report when this makes graph disconnected and whether unconstrained cost-optimal DP still has a valid path. Do not silently drop frames or teleport across infeasible segments.
6. Verify candidate transformations: all motor angles correspond to hypothetical URDF bounds; recalculated finite-difference jump, velocity (°/s), acceleration (°/s²) from recorded dataset timestamps; maximum motor deviation from recorded Action; maximum tool orientation ΔR; residual max; calibration-range consistency separately.
7. Explicit focus on shoulder_lift at f571→572 and any path switch around 570–574. Report chosen seed names per frame, chosen motor angles, bound contacts, biggest jumps and frame/joint. Note URDF ±100° vs recorded shoulder at f572 −100.923° and physical mapping remains unverified.
8. **Predeclare evaluation**: numerical target coverage 31/31 per direction; position residual ≤2 mm; max deviation ≤15°; one-frame jump ≤5°; velocity ≤100°/s; acceleration ≤2,000°/s²; tool ΔR ≤15°. These thresholds are study quality diagnostics, not manufacturer-certified safety limits. Report pass/fail for EACH mapping+direction and an aggregate. If impossible within candidate set, say so.
9. Report whether DP can improve the original greedy outcome but not overclaim. A greedy choice based on prior selected seed can influence the original candidate generation, and the new greedy recomputation from that pool is not necessarily numerically identical to historic greedy; document differences.

## Decision
This is **CONDITIONAL_NUMERICAL_SENSITIVITY**. Numerical DP results do not establish which LeRobot→URDF angle transformation is physically correct. Even if quality diagnostics pass, no ACT data generation (especially changing Action while leaving images fixed) or hardware replay is authorized.
